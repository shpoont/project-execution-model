# Maintaining the Project Execution Model

This repository develops and publishes a general model for turning a need into
a working result and learning whether it produces the intended benefit.
The [model](deliverables/project-execution-model.md) is the result people use;
the records described here support maintaining it.

## Purpose and Boundaries

The project serves people working alone or with human or AI contributors,
across software and other domains. The model should explain the work clearly,
remain usable on its own, and preserve the reasons, evidence and open questions
needed as work develops.

Repository organization follows [Project Structure 1.1.0](https://github.com/shpoont/project-structure/tree/v1.1.0).
Its baseline is recorded in [.project-structure.yaml](.project-structure.yaml).
That is separate from PEM's own release version. This organization guides work
on this repository; it creates no requirement for projects using PEM.

## Expectations and Decisions

A proposed change has a bounded scope and acceptance checks in its GitHub
issue or pull request. The complete current model remains authoritative;
proposals and examples do not silently change its rules. Significant decisions
and their reasons belong in the [decision log](docs/decision-log.md).

Delivery acceptance concerns the reviewed text, working links and assets,
consistent version information, and the agreed publication. The intended
benefit is that readers can understand and apply the model. Editorial reviews,
simulations and successful publication do not by themselves demonstrate that
benefit in real projects. Feedback and evidence from use inform later work.

Changes must preserve agreed substance unless a conceptual change is explicitly
accepted. Public records must be self-contained and must not expose personal
paths, private conversations or private operational records. The project adds
no mandatory runtime, work-management tool or documentation format for users.

The repository maintainer decides direction, accepts changes and authorizes
publication. Contributors prepare proposals and evidence within the agreed
scope. A completed review does not itself authorize merging or releasing.

## Continuing the Work

Use the [repository guide](docs/README.md) to find active agreements, working
materials, checks, decisions and delivery information. The
[contributor guide](CONTRIBUTING.md) explains how a change moves through review.
This is an ongoing maintained project: each increment has its own completion
boundary and any remaining obligations need an owner at handover.
